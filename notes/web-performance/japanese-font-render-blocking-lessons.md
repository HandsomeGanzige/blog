# 日文字体 CSS 优化复盘：为什么完整 CSS 与 FontFace JS 都不是答案

一个包含近 300 条 `@font-face` 的日文字体 CSS 阻塞了首屏。最直觉的优化是把它改写成 JavaScript、拆成多个文件，或者异步加载，但实验结果很反直觉：完整 FontFace JavaScript 会占用更多主线程时间，恢复完整 CSS 后，首屏又被同步样式表阻塞。

问题并不是 CSS 和 JavaScript 谁更快，而是两种方案都保留了同一批字体声明，只把成本放到了不同位置。

这次优化还没有得到最终答案，但留下了一套可复用的判断方法：先区分字体声明、字体文件下载和渲染门槛，再判断方案是否真的减少了首屏工作量。

## 声明了近 300 个字体，为什么不会下载近 300 个文件？

因为 `@font-face` 声明和字体文件下载是两件事。

当前字体由多个字重、每个字重数十个 Unicode 切片，以及少量独立字体组成，最终产生近 300 条字体声明。

每个日文字体声明都包含不同的 `unicode-range`：

```css
@font-face {
  font-family: 'JapaneseBrandFont';
  font-weight: 400;
  src: url('/fonts/japanese/regular-subset-41.woff2') format('woff2');
  unicode-range: U+3041-3095, U+30A1-30FE;
}
```

以上名称和 URL 仅为示例，不对应真实项目资源。

浏览器只有在页面实际使用某个字符，并且字体族、字重和样式匹配时，才会下载覆盖该字符的字体文件。

如果页面没有使用这个范围内的字符，字体文件不会被下载；只要使用了其中一个字符，对应的完整切片就会下载。这正是 [`unicode-range`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40font-face/unicode-range) 的设计目的。

因此，字体切片下载并不是最初怀疑的主要问题。浏览器已经能够按字符和字重选择字体文件。真正浪费的是：为了给浏览器提供这张映射表，页面必须先处理近 300 条声明。

> 字体文件已经按需下载，不代表字体声明也没有成本。

## 真正阻塞首屏的是下载，还是 CSS 解析？

当前完整 CSS 原始大小约为 0.5MB，包含超过 2,000 行和近 300 条声明。它通过 `<head>` 中普通的样式表链接加载：

```html
<link rel="stylesheet" href="/styles/japanese-fonts.css" />
```

以上路径是脱敏后的示例。

普通样式表默认是渲染阻塞资源。浏览器必须完成下载和处理，构建出 CSSOM 后，才能进行首次渲染。这个行为属于[关键渲染路径](https://web.dev/learn/performance/understanding-the-critical-path/)的一部分。

一次 Chrome Performance 记录中，这个请求位于 FCP 前的关键路径，占据约 200ms 的请求生命周期，而整个页面的 LCP 约为 0.5 秒。对于绝对时间已经较短的页面，这段等待仍然占据了较高比例。

但网络瀑布中的长条不能直接解释为“CSS 解析耗时约 200ms”。同一段接近一秒的 Performance 摘要显示，主线程时间主要消耗在脚本执行和渲染上，“加载”分类只占很小一部分。

这说明同步 CSS 的主要问题首先是它形成了一个渲染门槛。请求等待、传输、解压、解析和后续样式计算都会影响首屏，但仅凭网络条无法把它们分别量化。

本地静态压缩结果也揭示了另一个容易误判的地方：

| 内容 | 原始大小 | Brotli 估算 | 声明或注册数 |
| --- | ---: | ---: | ---: |
| 完整 `@font-face` CSS | 约 0.5MB | 约 13KB | 近 300 |
| 完整 FontFace JS | 约 64KB | 约 12KB | 近 300 |
| 仅保留常用字重的 CSS | 约 210KB | 约 12KB | 约 120 |

CSS 原始内容很大，但 Unicode 范围和声明结构高度重复，Brotli 可以把它压缩得非常小。完整 CSS 与完整 JS 的网络体积接近，差异主要发生在浏览器处理方式上。

## 为什么改成 FontFace JavaScript 仍然没有解决问题？

FontFace 版本把字体目录放进 JavaScript，通过双层循环注册所有字体：

```js
for (const weight of weights) {
  for (const bucket of buckets) {
    document.fonts.add(
      new FontFace('JapaneseBrandFont', `url("${fontUrl}")`, {
        weight,
        unicodeRange: bucket.unicodeRange,
      }),
    );
  }
}
```

以上字体名称为虚构示例。

它没有调用 `FontFace.load()`，所以字体文件仍然由浏览器按需下载。这个行为符合 [CSS Font Loading API](https://developer.mozilla.org/en-US/docs/Web/API/CSS_Font_Loading_API) 的设计。

问题是，注册过程需要 JavaScript 完成以下工作：

1. 下载并解析字体目录。
2. 执行双层循环。
3. 构造近 300 个 `FontFace` 对象。
4. 解析每个对象的 Unicode 范围和字体描述符。
5. 调用近 300 次 `document.fonts.add()`。
6. 更新 FontFaceSet，并可能触发垃圾回收和后续样式匹配。

CSS 版本可以使用浏览器内部优化过的原生样式解析器；JavaScript 版本则把同一批工作暴露到主线程。实验中观察到 JS 的执行时间更长，因此最终撤回。

加载时机也制造了新的两难：

- 异步脚本不阻塞 HTML 解析，但字体声明出现得更晚，字体请求、字体替换和最终文字布局也可能更晚。
- 同步 `<head>` 脚本可以尽早注册字体，却会同时阻塞 HTML 解析和主线程，失去了相对 CSS 的优势。
- React effect 不阻塞首屏，但执行时机明显太晚。
- 自定义文档模板只处理初始文档，客户端软路由不会重新执行其中的脚本。
- 共享页面元数据组件或 Layout 能覆盖软路由，却可能把字体目录带入非日文客户端包。
- 静态外部脚本可以跨页面缓存，但不会经过 Webpack 转换和压缩；直接 import JSON 又会污染组件依赖图。

这些集成问题都可以分别解决，却没有一个能减少近 300 次注册本身。实现越来越复杂，恰好说明优化层级选错了。

> 在决定代码放进文档模板、Head 还是 Layout 之前，先确认它做的工作是否应该存在于运行时。

## 尝试过的方案，分别解决了什么？

这次探索包含实际上线实验、构建原型和未实施分析。把它们放在同一张表中，更容易看到每种方案改变了哪一项成本。

| 方案 | 状态 | 改变的成本 | 主要问题或结论 |
| --- | --- | --- | --- |
| 删除开发态检查工具 | 已实施 | 删除无关开发代码和依赖 | 有价值，但与字体阻塞是两个独立问题 |
| 仅日文 HTML 加载完整字体 CSS | 已实施并保留 | 非日文页面不再承担字体 CSS | 缩小影响范围，没有减少日文页面的字体声明 |
| 完整 CSS 同步加载 | 当前基线 | 使用浏览器原生字体匹配与解析 | 外部 stylesheet 成为首屏渲染门槛 |
| 构建时扫描页面字符和 CSS 字重 | 做过原型 | 只输出页面需要的字体切片 | 动态文案、伪元素、表单属性、Canvas、客户端路由和继承字重让正确性分析复杂 |
| 共享 CSS 按内容 hash 缓存 | 做过原型 | 避免数千页面重复解析相同 CSS | 可以控制构建性能，但不能消除分析模型的维护成本 |
| 生成独立 hashed subset CSS | 做过原型 | 页面只请求自己的字体声明，且可以跨页面缓存 | 首屏仍有一个阻塞 CSS 请求 |
| JSON 作为唯一字体数据源 | 做过原型 | 目录可校验、版本可维护、CSS 可确定性生成 | 数据源更干净，但不会自动减少浏览器需要处理的声明 |
| 构建后内联最小 `<style>` | 做过原型 | 消除首屏字体 CSS 请求 | HTML 体积增加，不能跨文档缓存；动态内容仍需要后续覆盖 |
| load/idle 后加载完整 CSS fallback | 做过原型 | 动态内容和软路由不易缺字 | 会产生重复声明，也会削弱“真正移除完整 CSS”的目标 |
| 完整 FontFace JS 异步注册 | 上线实验后撤回 | 去掉同步 stylesheet 门槛 | 大量对象和 API 调用占用主线程，字体发现更晚 |
| 完整 FontFace JS 同步注册 | 上线实验后撤回 | 尝试让字体更早可用 | 同时阻塞解析和主线程，代价更高 |
| 每个字体切片一个 CSS | 分析后未实施 | 单个文件很小 | 可能产生数百请求，破坏压缩和调度效率 |
| 按字重拆分 CSS | 分析后未实施 | 减少首屏规则数量 | 多个文件会失去 Unicode 范围的跨字重压缩优势 |
| 修改全局字体作用域 | 已分析并部分调整 | 避免非日文页面使用日文字体 | 解决语言边界，不解决字体声明关键路径 |

一次旧构建产物扫描覆盖约 6,000 个 HTML，其中约 1,600 个日文页面只引用约 80 种不同 CSS 内容。通过内容 hash 复用扫描结果，构建性能并不是不可控制的；真正困难的是如何证明首屏字符、字重和动态场景都不会漏字体。

## 拆分为什么没有想象中简单？

最自然的想法是按字重拆分，只同步加载几个常用字重，其余字重延迟加载。

这确实可以把规则数从近 300 条降到约 120 条，但 Brotli 体积只减少约 1KB。因为数十组很长的 Unicode 范围会在不同字重之间重复，完整文件反而能够获得极高的压缩率。

如果每个字重单独生成文件，每个文件压缩后仍接近 12KB。多个文件的总传输量会远大于一个完整文件。

因此，按字重拆分的主要收益是减少解析规则，而不是减少网络字节；按字符切片拆分才可能同时减少规则数量和首屏内容，但它重新引入了构建时字符识别问题。

还可以选择把字体切片重新合并成较大的字体文件，用少量声明换取更大的字体下载。但这会失去浏览器已有的按字符下载能力，是另一种成本交换，而不是免费优化。

## 目前最值得继续验证的方向

截至目前，还没有经过严格 A/B 验证的最终方案。相对合理的方向是：

1. 保留原生 `@font-face` 和 `unicode-range`，继续让浏览器负责字体匹配与文件下载。
2. 构建时只为首屏 SSR 内容生成最小字体声明。
3. 将首屏声明内联，消除外部字体 CSS 请求。
4. 首屏之后再以非阻塞方式加载剩余声明。
5. 对动态文案、软路由和 Canvas 建立明确的覆盖策略，而不是无条件恢复完整同步 CSS。

这个方向的难点不是生成 CSS，而是建立可信的字符覆盖模型。它需要至少覆盖：

- SSR HTML 可见文本；
- 首屏实际使用的字体族、字重和样式；
- 实体字符、表单可见属性与 CSS `content`；
- 字重继承、关键字和无法解析的变量值；
- 首屏可能直接绘制字体的 Canvas；
- 客户端路由和接口返回的动态文字。

如果不愿承担这套分析复杂度，就需要接受系统字体首绘、后续字体替换，或者继续承担完整字体 CSS 的渲染阻塞。三者无法同时消失。

## 下一次字体性能优化，先问这五个问题

1. **瓶颈究竟是请求等待、解压解析、样式计算，还是字体文件下载？**
   Network 长条不能直接当作 CPU 解析时间，必须结合 Performance 主线程记录。

2. **方案是否减少了首屏声明数量？**
   如果仍然处理近 300 个字体，只是把 CSS 改成 JS，通常只是在转移成本。

3. **拆分后是否损失压缩和缓存？**
   原始文件变小不代表传输变小；重复的 Unicode 范围可能依赖跨规则压缩。

4. **字体正确性能够被怎样证明？**
   字符、字重、动态内容、Canvas 和软路由都可能让“看起来够用”的子集漏字。

5. **测试是否真的可比？**
   应在同一页面、相同设备与节流条件下，分别比较多轮冷缓存和热缓存结果，并同时记录 FCP、LCP、CLS、主线程任务和字体请求发现时间。

判断字体优化是否有效，可以浓缩为一句话：

> 不要先问应该用 CSS 还是 JavaScript；先问首屏究竟需要浏览器知道多少条字体声明，以及如何证明这组声明足够。
