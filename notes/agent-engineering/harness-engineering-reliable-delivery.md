# Harness Engineering：让 AI 编程从“生成代码”变成可靠交付

AI 能写出代码，不意味着它能稳定完成开发任务。它可能没有读到项目约束，修改了不该修改的模块，或者在编译通过后就宣布功能完成。

提高可靠性，不能只靠反复强调“认真一点”。更有效的办法，是把开发要求变成工作环境中的具体机制：让规则容易找到，让任务可以接续，让错误能够暴露，让完成有证据。

这就是 **Harness Engineering**：设计模型周围的指令、工具、环境、状态和反馈，使 Agent 的工作受到引导、检查与控制。

它不保证模型永远正确，而是让错误更容易被发现，让失败更容易恢复。

## 一、不要把所有要求都塞进提示词

提示词适合表达当前任务，但不适合独自承担整个项目的知识管理。

假设你让 Agent 给网站增加“修改昵称”功能。它至少需要知道：

- 昵称最长多少字符，是否允许为空；
- 页面通过哪个接口保存数据；
- 哪些目录允许修改；
- 应该运行什么检查。

如果这些要求只存在于某段聊天里，下一个会话就可能遗漏；如果全部复制进一份巨大说明，真正相关的规则又容易被淹没。

更合理的方式，是按信息职责分层：

| 信息 | 合适的位置 |
|---|---|
| 当前要完成什么 | 当前任务描述 |
| 项目的通用规则和导航 | 简短的入口文档，如 `AGENTS.md` |
| 产品规则、架构边界 | 对应专题文档 |
| 接口与实现细节 | 类型、代码及附近的测试 |
| 本轮进展与未完成项 | 任务状态和交接记录 |

**入口文档应该像地图，而不是百科全书。** 它告诉 Agent 去哪里找资料、哪些边界必须遵守、如何检查结果，而不是复制所有实现细节。

例如，入口可以只说明：

> 修改用户资料前，阅读用户资料规范。页面不能直接访问数据库，必须通过用户服务。修改后运行相关测试与类型检查。

这样既保留了关键约束，也给出了继续查找的路径。

### 写下规则，为什么还不够？

因为自然语言规则提供指导，却不会自动阻止违规。

“页面不能直接访问数据库”可以写进文档，但重要的依赖边界还应尽可能交给静态检查或自动化测试。一旦 Agent 违反规则，工具应返回明确错误，而不是等待它自己想起来。

可以采用一个简单分工：

> 文档解释为什么以及去哪里找；工具检查能够机械判定的规则；人工确认影响较大或存在歧义的决定。

并不是每条建议都值得做成检查器。优先自动化那些经常发生、代价较高、能够明确判断对错的问题。

## 二、让任务状态留在仓库里，而不是只留在对话里

长任务的难点不只是上下文容量，而是工作能否在中断后重新建立正确方向。

一句“昵称功能基本完成，继续处理”并不能帮助接手者判断：究竟哪里已经完成，哪里仍然缺失，“基本完成”又经过了什么验证？

更有用的交接记录可以很短：

```text
目标：用户可以修改昵称，刷新页面后仍然保留。

已完成：
- 保存接口与输入校验。
- 接口相关测试已通过。

未完成：
- 页面尚未接入保存接口。
- 尚未验证刷新后的展示。

下一步：
- 接入页面，再验证保存与刷新流程。
```

这份记录不是聊天摘要，而是下一次行动的入口。

### 为什么要一次完成一个小功能？

因为同时推进多个未完成目标，会让错误来源变得模糊。

如果一轮修改同时涉及昵称、头像和密码，保存失败可能来自共享接口、权限判断或页面状态。若先完整完成昵称修改，就更容易确定影响范围，也更容易检查和撤销。

“小功能”不等于“只改一个文件”。昵称修改可能需要同时修改页面、接口和测试，但它们服务于同一个可以验收的结果。

一个合适的工作单元应当具备：

- 明确的用户结果；
- 可识别的修改边界；
- 能够执行的验收方式。

开发循环可以因此收敛为：

```text
确认当前状态
→ 选择一个有边界的目标
→ 实现
→ 验证
→ 记录结果与剩余问题
```

### 有了交接记录，还需要重新检查吗？

需要。记录保存的是上一次的认知，仓库和运行环境可能已经变化。

恢复工作时，应重新检查当前代码、工作区差异和必要的基线检查。如果记录说测试通过，而当前测试失败，就不能继续把旧结论当作事实。

因此，状态文件最好保存验证入口、结果和未验证项，而不是用大量文字复制代码。

**交接记录负责指路，当前代码与重新执行的检查负责校准。**

## 三、把“完成”改成可以观察的结果

Agent 说“完成了”，只是一个结论，不是证据。代码能编译，也只能证明特定检查没有发现问题。

仍以修改昵称为例：

| 检查 | 能证明什么 |
|---|---|
| 类型检查 | 调用和数据类型满足静态约束 |
| 接口测试 | 给定输入时，接口执行预期行为 |
| 页面操作验证 | 用户能够输入、保存并看到反馈 |
| 刷新后检查 | 保存结果能够重新读取并展示 |

这些检查互相补充，不能用其中一个代替全部。

更重要的是，验收条件应该在实现前写清楚。例如：

> 输入合法昵称后可以保存；刷新后仍显示新昵称；空昵称被拒绝，并显示明确提示。

这比“实现昵称编辑并充分测试”更容易执行，也更容易暴露缺口。

### 为什么验证应该围绕行为，而不是实现方式？

因为只检查内部动作，可能漏掉用户真正关心的结果。

“保存函数被调用一次”不代表数据真的保存成功；“页面出现成功提示”也不代表刷新后数据仍然存在。

优先从用户结果反推检查，再用内部测试帮助定位问题。这样实现可以重构，验收目标却保持稳定。

还要防止验证结论被过度解释：

- 使用模拟接口通过测试，不代表真实服务可用；
- 页面显示了引用，不代表引用支持答案；
- 重试成功一次，不代表并发情况下没有问题。

证据必须与声明匹配。验证覆盖到哪里，完成声明就到哪里。

### 好的完成报告应该包含什么？

不必罗列全部操作过程，只需让接收者能够核对：

```text
完成：昵称编辑与保存。

验证：
- 类型检查通过。
- 接口测试通过。
- 已手动验证保存后刷新仍保留昵称。

未验证：
- 多设备同时修改时的行为。
```

这里展示的是报告格式，不是实际执行结果。

如果某项检查没有运行，应明确写“未运行”，并说明原因。诚实的验证缺口，比笼统的“应该没问题”更有价值。

## 如何为自己的项目搭建最小 Harness？

不要从生成一整套文档开始。先选择一个常见的小功能，为它准备三个东西：

1. **一个入口**：指出项目规则、相关资料和检查方法。
2. **一个任务记录**：写明验收条件、当前状态和下一步。
3. **一条验证路径**：能够从代码检查走到实际用户行为。

然后做一次刻意的中断：让新会话只依靠仓库材料继续工作。

如果它不知道读哪里，补导航；如果它不知道做到了哪一步，补状态；如果它无法判断是否完成，补验证。涉及删除、发布等高影响动作时，再加入明确的授权边界，而不是把所有事情都自动化。

Harness 的价值不在于文件数量，也不在于编排有多复杂，而在于一个具体问题：

> 当 Agent 理解错了、执行失败了或中途退出时，环境能否帮助下一步回到可核对的事实？
