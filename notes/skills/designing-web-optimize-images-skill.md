# 设计一个可信的图片优化 Skill：从自动化状态机到纯粹工具接口

图片优化 Skill 的主要风险不是编码能力不足，而是把确定性文件处理、项目上下文判断和用户授权混进同一套程序流程。脚本可以准确测量尺寸、转换格式，却无法仅凭图片内容决定页面需要多大、是否值得做响应式，也不能用一个状态字段证明用户真的批准了裁剪、删除或上传。

最终方案因此不追求端到端自动化，而是建立明确边界：脚本只提供可验证的下载、检查和编码能力；Agent 负责分析布局、选择参数和修改源码；用户决定改变构图、正式写入、删除及外部发布。边界清楚后，复杂的工作流状态机不再必要。

## 脚本只处理能够证明的事实

完整状态机曾经看起来更安全：它可以维护 manifest、图片编号、审批状态、源码切换、恢复和归档。但这些状态没有解决真正的不确定性。

文件名、alt、裁剪区域和响应式宽度取决于图片用途；源码引用又受 JSX、CSS、构建工具和项目目录约定影响。Agent 已经能够读取这些上下文并执行精确 patch，让图片脚本再实现一套源码切换只会复制能力。对话授权同样不能被 `approved` 字段替代，因为程序状态可能与用户实际同意的操作范围脱节。

最终接口只保留三个单一职责命令：

```text
download-image  → 将 HTTPS 来源保存为明确的本地快照
inspect-image   → 读取本地文件的客观属性
encode-image    → 按显式参数生成并验证 WebP
```

`inspect-image` 返回实际格式、尺寸、方向、压缩类型、页数和透明度，但不推荐目标尺寸或 quality。`encode-image` 负责自动旋转、sRGB 转换、限制尺寸和确定性编码，同时拒绝放大、覆盖文件及静态化动画。外部资产上传则交给独立能力处理，因为批准视觉候选不等于批准向外部系统写入数据。

## 本地快照建立输入一致性

检查和编码如果都直接接受 URL，同一张图片就会下载两次。远程内容可能在两次请求之间变化，导致 Agent 检查的是一份文件，实际编码的却是另一份文件。

解决方法不是增加共享缓存状态，而是先下载一次，再让所有后续操作使用同一个本地文件：

```text
远程 URL
  → 项目内本地快照
  → inspect
  → 多次 encode 尝试
  → 比较 source SHA-256
```

本地快照成为命令之间可见、可检查的事实边界。它减少重复请求，也允许 Agent 对同一份字节尝试不同尺寸和 quality。检查与编码返回的源文件哈希必须一致，否则候选结果无效。

源快照和候选图默认保存在仓库内被忽略的 `.agent-work` 目录。只有需要通过开发服务器验证页面布局时，候选图才临时进入 `public`。Git ignore 不会阻止公共目录内容进入构建产物，因此公开预览文件和引用必须在交付前清理。

## 验证指标必须对应真实问题

一张图片已经是有损 WebP，并不能证明它不需要优化。像素尺寸和编码体积是两个独立维度：如果页面只需要约 600 像素宽，`930 × 540` 的图片仍可能造成多余传输和解码；如果缩小后的候选反而更大，只能说明这次 quality 或编码参数不合适，不能反过来证明原始尺寸合理。

这条约束也使“按照片、插画或截图自动选择压缩模式”失去意义。内容分类无法稳定推出正确参数，同类图片对文字清晰度和颜色保真的要求也不同。编码器因此只接受显式 quality，候选是否合适由测量结果和实际渲染共同决定。

另一个验证错误来自 Alpha 通道。部分 PNG 虽然包含 Alpha 通道，但所有像素都完全不透明。如果验证器只保护 `hasAlpha`，就会拒绝没有保留冗余通道的有效输出。正确边界是区分文件结构和视觉语义：报告通道是否存在，但只要求编码结果保留真实透明度。

这两个案例指向同一原则：工具应报告事实并保护可见约束，不能让单次编码结果或表面元数据替代问题本身。

## 渲染优化属于工程上下文

普通 React 项目需要结合父容器、断点、`object-fit`、弹窗、轮播和下载用途计算真实展示上限，还要遵循现有的 import 或 public URL 模型。alt、固有尺寸和懒加载同样具有页面语义，不能由编码器从像素中推断。

Next.js 还需要检查实际版本、路由模式、图片配置、自定义 loader、CDN 和静态导出行为。当图片优化器正常工作时，通常提供一张合适的母图即可，由框架生成交付宽度；只有优化器被绕过且多视口收益明确时，才值得手动制作多尺寸文件。

响应式图片因此不是默认产物。Hero、Banner 或 LCP 图片在手机和桌面之间展示宽度差异明显时，Agent 应先提出宽度、`sizes` 和构图方案，获得同意后再生成变体。固定尺寸的后台缩略图、头像和图标则通常保留单一合理尺寸，避免用额外资源和标记换取有限收益。

## 测试保护工具契约

自动化测试只覆盖脚本能够承诺的行为：真实格式识别、方向尺寸、压缩类型、透明度、禁止放大和覆盖、动画拒绝、确定性输出、URL 脱敏、下载边界，以及 inspect 与 encode 的输入哈希一致性。

测试不会断言某张图应该使用特定 quality，也不会判断某个页面必然需要响应式图片。这些结论依赖布局和产品目标，冻结进测试只会把暂时经验伪装成永久规则。

从这个案例得到的经验性推论是：设计 Agent Skill 时，应先分离客观事实、上下文判断和用户授权。只有重复且需要确定性的操作适合进入脚本；显式文件、哈希和精确 patch 往往比隐藏状态机更容易验证。Skill 的价值不在于自动完成更多步骤，而在于让每个参与者只负责自己真正能够可靠完成的部分。
