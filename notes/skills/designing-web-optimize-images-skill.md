# 设计一个可信的图片优化 Skill：从自动化状态机到纯粹工具接口

开发一个图片优化 Skill，看上去像是一个很直接的问题：读取图片，调用 Sharp，调整尺寸，再输出 WebP。真正把它放进前端开发流程以后，问题却迅速变得复杂。图片可能来自 Figma、远程 URL、本地文件或项目已有资源；相同文件可能出现在 Hero、缩略图、弹窗和下载链接中；React 与 Next.js 的交付方式不同；“压缩成功”也不等于页面真的得到了优化。

这次设计最终没有把重点放在“让脚本自动完成更多事情”上，而是不断缩小脚本的职责，直到每个接口都足够明确、可验证。与此同时，把依赖页面布局、项目配置和用户意图的判断留给 Agent。这个过程比最后的三个命令更值得记录，因为它揭示了一个常见误区：工作流自动化得越完整，并不代表系统越可信。

## 起点：问题并不只是把图片转成 WebP

最初的需求来自 Next.js 图片优化，希望 Agent 在开发页面、引入图片时，能够主动注意图片尺寸、文件体积和响应式交付。但继续分析后发现，把能力写成 Next.js 专用 Skill 会过早限制问题范围。

普通 React 项目同样会遇到超大图片、错误懒加载、缺少固有尺寸、`srcSet` 配置不当等问题。图片也不一定来自代码仓库：它可能刚从 Figma 导出，可能是用户给出的 HTTPS 地址，也可能是已有线上资源。真正稳定的主体能力应该是“处理前端使用的栅格图片”，Next.js 只是其中一种需要条件读取的集成指导。

因此，Skill 被拆成两层：底层处理图片文件，回答格式、尺寸、字节和编码结果等客观问题；上层由 Agent 阅读项目代码，判断图片实际如何展示、应当生成多大、是否需要响应式交付，以及最终如何修改源码。

这个边界很重要。脚本擅长重复、确定、需要精确验证的工作；Agent 擅长从布局、上下文和用户意图中做判断。如果反过来，让脚本猜业务语义，让 Agent 手写底层编码细节，两边都会变得不可靠。

## 第一次设计：完整状态机带来的虚假安全感

早期方案试图把整个工作流装进脚本：为每张图片分配编号，维护 manifest 和状态流，自动切换与恢复源码引用，记录审批状态，生成归档，甚至把外部资产上传也纳入同一套流程。

这套设计看起来很完整。一次运行似乎可以从源文件一路走到正式发布，失败时也有状态可查。但在真实使用中，它带来了明显摩擦。

首先，Agent 本来就能理解并精确修改 JSX、CSS 和配置文件。让图片脚本再实现一套源码 switch/restore，不仅重复能力，还必须面对不同构建工具、不同资源引用形式和同一文件内多张图片的组合情况。

其次，用户是否同意裁剪、删除或上传，是对话里的授权语义。把一个 `approved` 字段写入 manifest，并不会让授权本身更可靠，反而容易让程序状态和真实对话发生偏差。

再次，文件名、alt、裁剪范围、响应式宽度和正式目录都依赖使用场景。即使脚本维护了完整状态机，这些决策仍然需要 Agent 完成。程序只是包裹了决策，并没有消除决策。

最后，一张图片的本地优化被迫携带运行 ID、状态迁移、恢复逻辑和归档清理，简单任务的操作成本明显高于其实际价值。

这次失败带来的第一个核心认识是：

> 自动化步骤多，不等于能力更可靠。脚本只有在输出客观事实，或执行确定性变换时，才真正增加可信度。

## 从工作流程序退回到三个纯粹接口

经过多轮精简，最终只保留三个公开命令：

```text
download-image
inspect-image
encode-image
```

它们分别处理远程快照、客观检查和确定性编码，彼此之间没有 manifest，也没有隐藏的工作流状态。

`download-image` 只做一件事：把一个 HTTPS 来源下载到调用方明确指定的本地文件。它拒绝覆盖已有文件，限制响应大小和重定向次数，并返回实际字节数、响应类型和 SHA-256。输出不会暴露 URL 查询参数或签名。

`inspect-image` 只接受本地文件。它返回解码后的真实格式、原始尺寸、考虑方向后的尺寸、压缩类型、页数、颜色空间、Alpha 通道和真实透明度等信息。它不会给出目标宽度、quality、优先级或“是否应该优化”的建议。

`encode-image` 同样只接受本地文件。调用方必须显式提供输出路径和 quality，可以选择宽高上限或已批准的裁剪区域。它负责自动旋转、转换到 sRGB、限制尺寸、编码为有损 WebP、验证输出并返回输入与输出哈希。它拒绝放大、覆盖已有文件以及把动画或多页图片静态化。

这样的接口看起来没有早期方案“智能”，但它们的承诺更容易理解：输入是什么、程序做了什么、输出能否验证，都可以直接回答。源码修改、文件命名和用户审批仍然由 Agent 管理，不再伪装成图片脚本的能力。

## 远程图片为什么必须只下载一次

在一次版本中，`inspect-image` 和 `encode-image` 都能直接接收 URL。这样使用方便，却意味着同一张图片会被下载两次：检查时一次，编码时再一次。

重复请求不只是浪费时间。远程地址可能在两次请求之间返回不同内容，尤其是动态资源、被替换的 CDN 对象或带时效行为的链接。此时 Agent 检查的是 A，实际编码的却可能是 B。即使两个命令都成功，也无法证明结果来自刚才看到的文件。

最终流程改成：

```text
远程 URL
  → 下载一次到项目内的本地快照
  → 检查这个本地文件
  → 用同一个本地文件尝试不同编码参数
  → 比较 inspect 与 encode 返回的 source SHA-256
```

本地文件在这里不是实现细节，而是命令之间清晰的事实边界。它避免了重复下载，也不需要引入缓存服务或 manifest。Agent 可以对同一份字节尝试多个尺寸和 quality；如果文件被意外修改，哈希不一致会立即暴露问题。

这个设计比“让两个命令隐式共享缓存”更简单，因为共享状态被替换成了一个明确、可检查、可以被普通文件工具理解的快照。

## 已经压缩过，不代表已经优化好

设计过程中遇到过一张约 `930 × 540` 的 WebP。它已经采用有损压缩，再编码后的候选文件有时反而更大，因此最初产生了“不需要优化”的倾向。

这个判断后来被证明混淆了两个独立维度：

1. 图片的像素尺寸是否超过页面真实需要。
2. 图片在某组编码参数下的文件体积是否合理。

如果页面最大只需要约 600 像素宽，那么 `930 × 540` 即使体积不算大，仍可能浪费传输、解码和内存，也可能触发 Lighthouse 的图片交付提示。反过来，一个缩小尺寸后的候选文件变大，只能说明本次选择的 quality 或编码参数不适合原文件，不能证明 resize 没有价值。

这个案例最终形成了一条稳定规则：始终分开评估几何尺寸和传输字节。一次编码实验只提供测量结果，不能替代对页面需求的分析。

也正是在这个案例之后，Skill 删除了“根据图片是照片、插画或 UI 截图自动选择压缩 profile”的设计。内容分类本身并不稳定，同类图片对文字清晰度和颜色保真的要求也可能不同。既然最后仍要通过实际体积和视觉结果判断，自动 profile 只是把启发式选择包装成了确定性能力。

最终编码器只保留标准有损 WebP，quality 必须由 Agent 显式给出。Agent 可以根据候选效果继续尝试，但脚本不会声称某种内容分类天然对应某个正确参数。

## Alpha 通道不等于真实透明

另一个问题出现在一组 Figma 导出的 PNG 上。这些文件都有 Alpha 通道，但每个像素的 Alpha 值都是完全不透明。旧验证逻辑只检查元数据里的 `hasAlpha`，于是要求输出文件也必须带 Alpha，导致正常的 WebP 被误判为“没有保留透明度”。

问题的本质是把“文件结构包含某个通道”和“图片实际使用该视觉属性”当成同一件事。

修复后，检查结果明确区分：

- `hasAlpha`：文件结构中是否存在 Alpha 通道。
- `hasTransparency`：像素中是否真的存在透明度。

编码验证只保护真实透明度。如果输入只是带着一个完全不透明的冗余通道，输出不必为了形式一致而保留它。

这个案例说明，即使脚本只负责客观事实，也要确保事实与真正要保护的性质相对应。元数据不是目的，视觉结果才是验证边界。

## 工作目录约定也是产品体验的一部分

一次 Figma 图片优化任务中，Agent 已经在一个明确的前端仓库里工作，却把候选文件留在系统 `/tmp`，最后又询问用户应该把它们保存在哪里。

这不是编码错误，却是明显的使用体验缺陷。当前仓库已经提供了足够上下文：它应该自然成为本次任务的工作项目。Figma、远程 URL 或外部文件只改变图片来源，不应该让 Agent 忘记目标项目。

最终约定使用项目内、被 Git 忽略的目录：

```text
<repo>/.agent-work/image-opt-sources/<task-slug>/
<repo>/.agent-work/image-opt-preview/<task-slug>/
```

源快照和候选文件都在当前项目内，便于查看、比较和继续处理。系统临时目录只用于真正可以丢弃的诊断中间物。

只有当候选图必须由开发服务器提供，才能验证页面里的 URL、布局或框架行为时，才暂时复制到：

```text
<public-dir>/__image-opt-preview__/<task-slug>/
```

这里还有一个容易忽略的风险：Git ignore 只影响版本控制，并不会阻止 `public` 目录内容进入构建产物。公共预览引用和文件必须在构建或交付前清理，不能因为它未被 Git 跟踪就把它当成不可部署内容。

## React 与 Next.js 的指导为什么不属于编码脚本

图片文件生成以后，如何在页面里使用仍然是工程决策。

普通 React 项目需要检查图片的真实 CSS 尺寸，而不是只看 `<img>` 上的 `width` 和 `height`。父容器、网格列宽、断点、`object-fit`、弹窗、轮播、放大查看和原图下载都可能改变所需尺寸。Agent还要遵循项目现有的资源模型：由 bundler import 图片，还是通过 public URL 引用。

渲染层还包含可访问性和性能语义。内容图片需要有意义的 alt；装饰图片应使用空 alt；已知宽高可以帮助避免布局偏移；可能成为 LCP 的首屏图片不应盲目懒加载；CSS background 只有在装饰性场景下才合适。

Next.js 需要更多上下文。Agent必须先读取实际安装版本、Pages Router 或 App Router、`next.config`、`images.unoptimized`、设备尺寸、自定义 loader、远程域名规则、CDN 和静态导出行为。不同版本的 `next/image` 接口并不完全相同，因此不能把最新写法套进旧项目。

当 Next Image 优化器正常工作时，一般只需要提供一张质量合理的母图，让框架生成交付宽度。预先制作整组响应式文件不仅重复框架能力，还会增加资源维护成本。只有优化器被绕过、静态导出不提供转换，或项目明确使用自己的图片交付机制时，才考虑手动生成宽度变体。

这些判断依赖源码和运行配置，无法由一个图片编码脚本可靠完成。因此它们被保留为 Agent 条件读取的工程指导，而不是继续增加 CLI 参数。

## 响应式图片不是默认答案

“图片优化”很容易演变成“为每张图生成一套断点”。这同样是过度自动化。

响应式图片只有在不同设备的展示宽度差异足够大时才值得引入，例如官网 Hero、Banner、可能的 LCP 图片，或者桌面端大图会原样发送给窄屏设备。项目还需要有可靠的选择机制，例如 Next Image、CDN 转换，或正确实现的 `srcSet` 与 `sizes`。

当这些信号出现时，Agent应先提出方案，而不是立即生成文件。方案要说明推荐宽度、`sizes` 如何映射真实布局、这是普通分辨率切换还是需要不同构图，以及会新增哪些资源和代码。只有用户同意后，才制作多个版本。

后台缩略图、头像、图标和固定尺寸 UI 截图通常没有这样的收益。为它们增加 `<picture>`、多份文件和复杂 `sizes`，可能比节省的流量更昂贵。

因此，响应式指导的默认行为不是“执行”，而是“在收益明确时提出一个可以被用户评估的建议”。

## 把外部资产上传拆出图片优化流程

早期工作流还尝试把对象存储上传、资产记录创建和失败重试纳入图片优化 Skill。后来已有专门负责资产发布的能力，这部分便从图片优化中彻底移除。

拆分后的边界是：图片优化只产生经过用户确认的本地正式文件；资产上传再接收这个文件，完成外部系统写入并返回 URL。

这种拆分不仅减少代码。它把两种完全不同的授权分开了：用户同意某个视觉候选，不等于同意向外部系统写入数据。外部上传失败也不应污染本地图片候选状态。

一个通用 Skill 如果必须了解某个资产管理系统的目录、Token 和记录状态，就很难在其他项目复用。把集成留给专门 Skill，图片优化主体才能真正保持通用。

## 测试保护的是脚本承诺，不是 Agent 的主观判断

最终测试覆盖的重点包括：

- 从解码结果识别实际格式，而不是信任扩展名。
- 区分原始尺寸与考虑方向后的尺寸。
- 识别 WebP 的有损与无损编码事实。
- 区分 Alpha 通道和真实透明度。
- 拒绝放大、越界裁剪、动画静态化和文件覆盖。
- 验证相同输入与参数产生确定性输出。
- 返回输入和输出的 SHA-256。
- 确保远程内容只下载一次。
- 覆盖 URL 脱敏、重定向、超时和大小限制。
- 确保 inspect 与 encode 拒绝直接接收远程 URL。
- 保持公开 CLI 数量和职责稳定。

测试不会断言“这张图片应该使用 quality 82”，也不会断言某个页面一定需要响应式图片。这些结论依赖视觉要求、实际布局和产品目标，不是脚本能够证明的事实。

这样的测试边界避免了另一种常见问题：为了让主观策略看起来稳定，把暂时的经验值写成永久规则。测试应该保护工具承诺，而不是冻结 Agent 的判断空间。

## 最终得到的经验

这次迭代最重要的变化，不是增加了多少图片处理能力，而是逐渐明确什么不应该由程序完成。

程序适合回答“这份文件是什么”“变换后得到什么”“两次操作是否基于同一份字节”。Agent适合回答“这个页面需要多大”“是否值得做响应式”“什么文件名和 alt 能表达真实含义”。用户则保留对裁剪、正式写入、删除和外部发布的最终决定。

当这三类职责混在一起时，系统需要状态机来维持表面秩序；当边界清楚后，本地文件、哈希和精确 patch 已经足够构成可靠工作流。

从这个案例可以进一步推导出一些适用于其他 Agent Skill 的经验：先区分客观事实和上下文判断；只把重复且需要确定性的操作写进脚本；不要用程序字段模拟对话授权；优先选择显式文件和可验证输出，而不是隐藏的跨命令状态；把工作目录和清理方式也视为接口的一部分。

这些是从本次实践中得到的经验性推论，并不是所有 Skill 都必须采用同一结构。但它提供了一个很有用的检查问题：如果移除某段自动化以后，Agent仍然能更清楚、更可靠地完成任务，那么那段自动化可能从一开始就不属于工具接口。
