# Web 图片优化 Skill：工作流程与使用边界

在前端开发中，“把这张图片压小一点”通常不是一个完整需求。图片最终应该多大，取决于它在页面中的展示尺寸、设备像素比、响应式布局，以及项目是否已经提供图片转换能力。

`web-optimize-images` 将图片优化中的职责分成三层：

- 脚本负责下载、检查和编码能够验证的文件；
- Agent 负责理解 React 或 Next.js 项目中的实际使用场景；
- 用户负责批准正式文件写入、源码修改、裁剪和删除。

这种分工的目的不是自动执行尽可能多的操作，而是让每一步都能够解释、验证和撤销。

## 什么情况下会触发？

当 React 或 Next.js 开发任务引入、导出、下载、替换图片，或改变图片渲染方式时，Agent 应主动使用这个 Skill。用户明确提出压缩、检查、缩放、转换 WebP 或响应式优化时，也会触发。

例如：

| 任务 | Skill 的关注点 |
| --- | --- |
| `帮我优化这张远程 Hero 图片` | 下载一次、检查页面展示尺寸、生成候选图 |
| `把这个 Figma 节点中的图片导出并优化` | 提取位图、保留 SVG、按设计尺寸编码 |
| `检查这次页面开发新增的图片` | 只检查当前任务涉及的资源，不扫描无关文件 |
| `这个 Banner 是否需要移动端尺寸？` | 分析多视口收益，并在生成多个版本前提出方案 |

对于尺寸和体积已经合理的普通资源，Skill 默认保持安静，不为了展示能力而重复编码。

## Agent 实际会怎样处理图片？

远程图片不会在检查和编码时分别下载。Agent 会先把 URL 下载为项目内的一份本地快照，然后所有后续操作都使用这份文件：

```text
远程 URL
→ 下载一次到项目临时目录
→ 检查格式、尺寸、体积和透明度
→ 结合页面代码决定候选尺寸和质量
→ 编码候选图片
→ 视觉检查
→ 展示正式应用方案
→ 用户批准后写入资源目录并修改引用
```

下载、检查和编码都会返回源文件的 SHA-256。Agent 会核对这些哈希，确保“被编码的文件”就是“刚才检查过的文件”。

如果检查和编码各自重新请求远程 URL，两次得到的内容可能不同。先保存本地快照既避免了这种不一致，也省去了重复下载。

## 脚本会自动决定压缩策略吗？

不会。脚本只处理能够通过输入和输出验证的操作。

图片编码器需要明确的目标尺寸和质量参数。它不会根据图片内容自动猜测所谓的“照片模式”或“图形模式”，也不会自行决定页面需要多大的图片。

Agent 会结合以下信息提出候选方案：

- 图片的真实展示尺寸；
- 可能使用的设备像素比；
- 父容器和响应式断点；
- 原文件的像素尺寸和体积；
- 图片是否还有放大、下载或共享用途；
- 项目已有的图片交付能力。

像素尺寸和文件体积会分开判断。一张已经压缩过的图片仍然可能因为像素尺寸远超展示需求而值得缩放；一次编码结果变大，也只能说明当前质量参数不合适，不能证明原图尺寸合理。

## React 项目会检查什么？

在普通 React 项目中，Agent 会检查图片真实的 CSS 展示范围，而不是只看 `<img>` 上的 `width` 和 `height`。

主要关注：

- 父容器、Grid、断点和 `max-width`；
- `object-fit` 和 `object-position`；
- 图片是否还用于弹窗、轮播、放大或原图下载；
- 项目采用静态 import 还是公开静态路径；
- `alt`、布局偏移和懒加载是否合理；
- CSS `background-image` 是否确实属于装饰内容。

固定尺寸的图标、头像、后台缩略图和界面截图，通常只需要一个合理尺寸的图片，不值得增加复杂的响应式标记。

对于可能成为 LCP 的首屏图片，Agent 不会盲目使用懒加载；对于非首屏图片，则会结合项目现有习惯判断是否使用原生懒加载。

## Next.js 项目有什么不同？

在 Next.js 项目中，Agent 会先读取实际安装的 Next.js 版本、Router 类型和图片配置，再决定如何使用 `next/image`。

需要检查的内容包括：

- 图片优化是否被禁用；
- `deviceSizes` 和 `imageSizes`；
- 远程图片域名规则；
- 自定义 loader 和静态导出行为；
- 当前版本支持的 fill、priority 或 preload 写法。

如果 Next.js 图片优化器正常工作，通常只需要提供一张合适的高质量母图，让框架生成实际交付的宽度。此时手动制作整套多尺寸文件，往往只是重复框架已经能够完成的工作。

如果图片优化器被禁用或绕过，Agent 才会进一步判断是否值得手动生成多个尺寸版本。

## 会主动询问是否制作响应式图片吗？

会，但不会对每张图片都询问。

以下场景通常值得提出多尺寸方案：

- 官网、营销页或内容网站；
- Hero、Banner 或可能成为 LCP 的图片；
- 手机与桌面的展示宽度差异明显；
- 大图会被直接发送给窄屏设备；
- 框架或项目已有可靠的宽度选择机制。

Agent 在询问时应该先说明：

- 为什么响应式图片可能有收益；
- 建议生成哪些宽度；
- `sizes` 应该如何对应真实布局；
- 会新增哪些文件和修改哪些代码；
- 是否只做分辨率切换，还是涉及不同构图。

获得同意后，才会生成多个版本或修改 `<picture>`、`srcSet`、`sizes` 等标记。

分辨率切换和构图裁剪是两件不同的事。即使用户同意生成多个宽度版本，也不代表同意修改移动端构图。

## 哪些操作不会自动执行？

这个 Skill 有几条明确边界：

- 不会放大分辨率不足的图片；
- 不会把 GIF、APNG 或动画 WebP 静态化；
- 不会在未经同意时裁剪或改变构图；
- 不会默认给所有图片生成多个断点版本；
- 不会因为候选文件存在就直接覆盖正式资源；
- 不会自动删除仍有其他引用的原始图片。

候选文件默认保存在项目忽略的临时目录。只有需要在真实页面中验证浏览器行为时，才会临时放入项目可访问的静态目录。

验证结束后必须移除临时引用和文件，避免把预览资源带入正式构建。

## 推荐的使用方式

发起任务时，尽量同时提供图片和使用场景：

```text
优化这张 Hero 图片。桌面端最大显示宽度是 1440px，
移动端基本占满屏幕，请判断是否值得做响应式版本。
```

然后依次检查：

1. Agent 找到的真实展示尺寸和其他引用；
2. 候选图片的尺寸、质量、体积和节省比例；
3. 候选图在代表性展示尺寸下的清晰度；
4. 响应式方案中的宽度和 `sizes` 是否符合布局；
5. 最终文件名、正式目录、代码修改和删除操作。

可以用一条规则理解整个流程：

> 文件事实由脚本证明，页面策略由 Agent 判断，正式变更由用户授权。

只有把这三层分开，图片优化才能在保持自动化效率的同时，仍然可解释、可验证和可控。
